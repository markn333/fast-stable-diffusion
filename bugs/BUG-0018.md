# BUG-0018: a dropped Google Drive mount surfaces as `OSError: [Errno 107] Transport endpoint is not connected` from `import gradio`
- Date: 2026-08-25
- Status: Mitigated (guard added; not yet exercised on Colab)
- Severity: Medium

## Symptom

```
File "modules/initialize.py", line 23, in imports
File "gradio/__init__.py", line 62, in <module>
  from gradio.deploy_space import deploy
File "gradio/deploy_space.py", line 11, in <module>
  repo_directory = os.getcwd()
OSError: [Errno 107] Transport endpoint is not connected
```

## Root Cause

**Not a dependency problem.** Errno 107 is `ENOTCONN`, raised by the FUSE layer when the Google
Drive mount has gone away while something still points into it.

The Start cell does `%cd /content/gdrive/<...>/stable-diffusion-webui/modules/` and then launches
`webui.py` from there, so the process's **working directory lives on the Drive mount**. When the
mount drops mid-session, the first thing to touch the cwd fails — and here that happens to be
`os.getcwd()` at line 11 of `gradio/deploy_space.py`, during `import gradio`. The traceback
therefore points at gradio, which has nothing to do with the actual fault.

A dead FUSE mount is not the same as an unmounted one: `/content/gdrive` still exists and
`drive.mount()` still reports success. The breakage only appears when a syscall actually reaches
through it.

Colab drops the mount for reasons outside the notebook's control — idle timeouts, a Drive-side
hiccup, or heavy I/O. The previous session moved ~12 GB through it (see BUG-0017), which is exactly
the kind of load that provokes this.

## Fix (mitigation)

The mount cannot be made reliable from inside the notebook, so the goal is to fail clearly and to
self-heal where possible.

**Connect Google Drive cell** — verify the mount rather than trusting `mount()`'s return, and force
a clean remount if it is stale:

```python
try:
  drive.mount('/content/gdrive')
  os.listdir('/content/gdrive')   # a dead FUSE mount still looks mounted until something touches it
except OSError:
  print('Drive mount is stale, forcing a remount...')
  drive.mount('/content/gdrive', force_remount=True)
```

**Start Stable-Diffusion cell** — refuse to launch on a dead mount, and say what to do:

```python
try:
  os.getcwd()
except OSError:
  os.chdir('/content')            # the working directory itself was on the dead mount
sdpath = f'/content/gdrive/{mainpth}/sd/stable-diffusion-w{blsaphemy}'
if not os.path.isdir(sdpath):
  raise SystemExit(
      '✘ Google Drive is not mounted, or the mount has dropped.\n'
      '  1. Re-run the "Connect Google Drive" cell (it force-remounts a stale mount).\n'
      '  2. If that does not help: Runtime > Restart runtime, then run the cells from the top.\n'
      f'  (looked for: {sdpath})')
```

The `os.chdir('/content')` matters: if the cwd itself is on the dead mount, even printing a
diagnostic can fail, so the guard steps off the mount before reporting.

## Changed Files
- `fast_stable_diffusion_AUTOMATIC1111.ipynb` — Connect Google Drive cell, Start Stable-Diffusion cell

## Recovery (for a session already in this state)

1. Re-run the **Connect Google Drive** cell — with the fix above it force-remounts a stale mount.
2. If the mount still refuses: **Runtime > Restart runtime**, then run the cells from the top.
   `force_remount` cannot always repair a FUSE endpoint that the kernel has already torn down.

Nothing needs reinstalling on Drive; the webui directory and models are intact — only the mount
between the runtime and Drive was lost.

## Prevention

- Distinguish "mounted" from "working". `drive.mount()` returning successfully says nothing about
  whether the endpoint is alive; only a syscall through it does. Check with a real access.
- A guard is worth adding wherever a cryptic errno would otherwise be attributed to the wrong
  component. This traceback blames `gradio`, and the next person to see it will start by checking
  gradio versions — which is precisely the wasted session this project keeps paying for
  (see BUG-0015's prevention notes).
