# BUG-0021: generation results never reach the browser — gallery clears on completion, Save fails with `JSONDecodeError`
- Date: 2026-08-26
- Status: **Diagnosed, workaround shipped.** gradio's websocket queue never delivers results here; plain HTTP does. `--no-gradio-queue` is now the default. The queue itself is still unexplained
- Severity: High

## Symptom

Image generation works — but nothing comes back to the page.

1. During generation the image is visible; **the moment it completes the gallery area goes blank.**
2. Pressing **Save** ("save the image to a dedicated directory") errors:

```
*** Error completing request
*** Arguments: ('', [], False, -1) {}
    File "modules/ui_common.py", line 76, in save_files
      data = json.loads(js_data)
    json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

The images themselves are fine: `Model loaded in 266.9s`, twenty batches of `100% 20/20`, and the
PNGs are on Drive under `outputs/txt2img-images/`. No traceback is printed when generation finishes.

## Root Cause

`*** Arguments: ('', [], False, -1)` is the whole diagnosis. Those are the inputs A1111 binds to the
Save button:

```python
save.click(
    fn=call_queue.wrap_gradio_call(save_files),
    _js="(x, y, z, w) => [x, y, false, selected_gallery_index()]",
    inputs=[generation_info, result_gallery, html_info, html_info],
    ...
)
```

- `generation_info` = `''` — should hold the generation parameters as JSON
- `result_gallery` = `[]` — **the gallery is genuinely empty**, not merely blank on screen

Both are outputs of the txt2img event. They are empty because **the result of that event never
arrived in the browser**, so the components still hold their initial values and the browser sends
those back when Save is clicked. The blank gallery follows from the same fact: A1111 draws the live
preview as a separate overlay element on top of the gallery (`progressbar.js`) and removes it when
generation ends — revealing the gallery underneath, which was never populated.

So one cause explains both symptoms, and it is a **transport** failure, not a generation failure.

gradio 3.41.2 delivers event results over a **websocket**:

```python
# gradio/routes.py
from starlette.websockets import WebSocketState
@app.websocket("/queue/join")
    await websocket.accept()
    ...
```

The stack around that websocket has drifted far from what gradio 3.41.2 was built against:

| component | what gradio 3.41.2 / A1111 expect | what the current notebook installs |
|-----------|-----------------------------------|-----------------------------------|
| starlette | 0.26.x (A1111 pins `fastapi==0.94.0`) | **0.40–0.50** (via our `fastapi==0.125.0`, BUG-0016) |
| websockets | `<12.0` (gradio's own pin) | 11.0.3 — pure-python wheel, no cp313 build |
| uvicorn | `>=0.14.0`, unpinned | 0.52.4, which **unconditionally** selects its sans-I/O websocket implementation |

A websocket that closes or drops a message produces **no traceback** — disconnects are ordinary
events — which is exactly why generation completes silently and nothing appears.

## Workaround shipped

A1111 has a first-class switch for this:

```
--no-gradio-queue   Disables gradio queue; causes the webpage to use http requests instead of
                    websockets; was the default in earlier versions
```

```python
# webui.py
if not cmd_opts.no_gradio_queue:
    shared.demo.queue(64)
```

The Start cell now exposes it as a notebook parameter, defaulting to on:

```python
Disable_Gradio_Queue = True #@param {type:"boolean"}
queue_arg = "--no-gradio-queue" if Disable_Gradio_Queue else ""
```

and passes `$queue_arg` to all three launch invocations.

This sidesteps the websocket entirely and costs very little: A1111 does not use the gradio queue for
progress — live previews and the progress bar come from its own `/internal/progress` HTTP endpoint,
so they keep working.

**It is also the experiment.** Leaving the box ticked and unticking it is a single-variable A/B:

- gallery works with the box ticked, breaks unticked → confirmed, the websocket transport is the
  fault, and the flag is a legitimate permanent answer (upstream calls it the earlier default)
- broken either way → the transport is innocent and the fault is in the event result itself; the
  next step is the browser's Network → WS tab to read the `process_completed` payload

## Prevention

- **A silent failure is still a lead.** No traceback at completion was the most informative signal in
  this investigation: it ruled out generation and saving, and pointed at a transport where
  disconnects are not errors.
- **Read the arguments in `*** Error completing request`.** A1111 prints the bound inputs, and
  `('', [], False, -1)` said the component state was empty before any theory was needed.
- When a version pin is chosen for one property, note what was *not* verified. BUG-0016 picked
  `fastapi==0.125.0` as "the newest release that still supports pydantic v1", and the import chain
  was checked — but the queue websocket was not, and A1111 pins `fastapi==0.94.0` precisely because
  the whole starlette layer moves with it.

## Update 2026-08-26 (2): the browser console names it — and invalidates the previous A/B

```
/run/predict:1  Failed to load resource: the server responded with a status of 504 ()
```

**504 Gateway Timeout on `POST /run/predict`.**

With `--no-gradio-queue`, gradio submits a generation as **one long synchronous HTTP request** and
waits for the whole thing. That run was eight batches at ~43 s each — roughly six minutes. The
gradio.live tunnel cuts the request off long before it finishes, so the browser receives a 504 and
no data at all. Everything else follows:

- the server generates, saves the PNGs and raises nothing — it never learns the client gave up
- the page's components stay at their initial values
- Save therefore posts `('', [], False, -1)`
- the live preview kept working because `/internal/progress` is short polling, not the long request

### The previous A/B was contaminated

The conclusion "the websocket is not the cause" is **withdrawn**. Both paths fail, but for different
reasons:

| transport | failure |
|-----------|---------|
| queue on (websocket) | unknown — still unexplained |
| queue off (HTTP) | **504 from the tunnel**, an artefact of the workaround itself |

Identical symptoms, different mechanisms. Turning off the queue did not test the websocket
hypothesis at all; it swapped one broken path for another broken path. Nothing about starlette,
uvicorn, `websockets` or the BUG-0016 `fastapi` pin was actually cleared.

### Default reverted

`Disable_Gradio_Queue` now defaults to **False**. `--no-gradio-queue` cannot work for multi-batch
runs on a tunnel: the queue exists precisely so that no single HTTP request has to stay open for the
length of a generation.

### The experiment that actually separates the two

Generate **one image at low step count** (~20-30 s end to end) with the queue on:

- **gallery populates** → there is no second bug; the failure is duration-related, and the fix is
  about keeping the connection alive (queue on, and possibly ngrok instead of the gradio.live share
  tunnel, which the notebook already supports via `Ngrok_token`)
- **still blank after 25 s** → there is a genuine second fault on the websocket path, and it is
  worth reading the WS frames

Duration is the one variable that has never been controlled in this investigation — every failing
run so far has been a long multi-batch job.

### Not related

The rest of that console output — `contentscript.js`, `ObjectMultiplex`, `app-init-liveness`,
`MaxListenersExceededWarning` — comes from a **browser** extension (a wallet extension injecting
into every page), not from the WebUI.

## Update 2026-08-26 (3): duration ruled out, and the link is alive

`Launch flags: --share` — queue on, extensions on. **One batch, one image, 50 seconds**:

```
100% 20/20 [00:50<00:00,  2.51s/it]
*** Arguments: ('', [], False, -1) {}
```

Same failure. **Duration is not the cause**, so the earlier 504 was purely an artefact of
`--no-gradio-queue` and nothing more.

Two things this run establishes:

1. **The browser↔server link works in both directions.** The Save click reached the server — that is
   how we are reading its traceback at all. So there is no dead socket and no severed tunnel; the
   page can talk to the backend and the backend answers.
2. **Neither side reports an error.** txt2img raises nothing (it would print its own
   `*** Error completing request`), and the browser console shows no JS exception — only a wallet
   browser extension's noise and `civitai_helper.js` logging `sd version is: 1.10.1`.

So the txt2img response is either arriving empty, or arriving and not being applied to the
components. Not a transport failure, not a timeout, not a crash.

`Test_Disable_Extensions = True` (`--disable-extra-extensions`) is the one-flag test.

## Update 2026-08-26 (4): root cause found — BUG-0022

Launching with `--disable-extra-extensions` removed the extension chatter and exposed what had been
printing all along:

```
<Queue at 0x7aca9b4c6fd0 maxsize=0 tasks=2> is bound to a different event loop
```

uvicorn 0.50+ always selects its sans-I/O websocket implementation, which creates a per-connection
`asyncio.Queue` on uvicorn's loop; gradio 3.41.2 runs its queue coroutine on another loop and the
resulting `RuntimeError` is swallowed by a bare `print(e)` at `gradio/queueing.py:464`.

That single swallowed exception is this entire bug: no event result is ever delivered, which is why
the gallery blanks, **PNG Info stopped working**, and Save receives `('', [], False, -1)` — while
clicks in the other direction kept working perfectly.

Fixed by pinning `uvicorn==0.49.0`. Full analysis, including the local venv experiment that settled
it, in bugs/BUG-0022.md.

Note that extensions were never the cause — disabling them was still what made the bug findable.

## Update 2026-08-27: the missing test finally ran — and it separates the halves

```
Launch flags: --share --no-gradio-queue
100% 20/20 [00:49<00:00,  2.48s/it]
```

No `*** Error completing request`, and **the image appears in the gallery**.

The matrix is complete:

| queue | generation length | result |
|-------|-------------------|--------|
| on (websocket) | long, multi-batch | fails |
| on (websocket) | short, 50 s | fails |
| off (HTTP) | long, multi-batch | fails — 504 from the tunnel, an artefact of the flag |
| **off (HTTP)** | **short, 49 s** | **works** |

**gradio's websocket queue is the fault.** Delivery over plain HTTP is fine; nothing upstream of
transport is broken. Everything that looked like a separate bug — blank gallery, dead PNG Info,
`Save` receiving `('', [], False, -1)` — was one undelivered result, and it is specific to the
queue path.

### Shipped

`Disable_Gradio_Queue` now defaults to **True**. Strictly better than the alternative: with the
queue on, nothing works at all; with it off, everything works up to the tunnel's patience.

**The trade-off is real and stated in the cell**: each generation becomes one long synchronous POST,
and gradio.live returns a 504 once a run takes a few minutes. A multi-batch job will still fail that
way. `Ngrok_token` (already supported by the Start cell) gives a tunnel that is not gradio.live's,
and is the answer for long batches until the queue itself is fixed.

### What is still unexplained

Why the queue fails. Ruled out so far: generation, saving, extensions, duration, the transport being
dead in either direction, uvicorn's websocket implementation (`uvicorn==0.49.0` is installed and
changes nothing), and `fastapi`/`transformers`/`open_clip` versions.

The remaining suspect is the layer under it, first observed only two runs ago:

```
starlette==0.50.0   anyio==4.14.2
```

gradio 3.41.2 was written against starlette 0.26/0.27 and **anyio 3.x**, and its queue is built on
exactly the primitives anyio 4 reworked — `run_coro_in_background`, blocking portals, cross-loop
handoff. Every starlette in range, **including 0.50.0**, declares `anyio<5,>=3.6.2`, so anyio can be
moved on its own:

```python
!pip install anyio==3.7.1 -q      # last 3.x, pure-python wheel
```

That is a genuine single-variable experiment, and a cheap one now that restarts are warm (this run
booted in 31 s): install it, untick `Disable_Gradio_Queue`, generate once. If the gallery fills, the
queue is repaired and the HTTP workaround can go back to being optional.

## Update 2026-08-27 (2): batch 50 used to work over gradio.live

Reported by the user: **a few days ago, before the Colab base image update, batch 50 ran fine over
the ordinary `--share` tunnel.** That is roughly 35 minutes of generation.

This reframes the 504 completely. gradio.live was never the limitation:

- **with the queue working**, a generation is *not* a long HTTP request. The browser joins the queue
  (a short call) and the result arrives later over the websocket. Duration is irrelevant, which is
  why batch 50 was fine.
- **`--no-gradio-queue` converts the same job into one synchronous POST held open for the whole
  generation.** *That* is what gradio.live refuses, and no tunnel is really meant to hold a 35-minute
  request open.

So the 504 is not a property of gradio.live that ngrok can be swapped in to avoid. It is a direct
consequence of the workaround, and it puts a ceiling of a few minutes on any run.

### What this changes

**Fixing the queue is the fix, not changing tunnels.** Restoring it restores batch 50 over the
tunnel that was already working, with no account, no interstitial and no new failure modes. ngrok is
still worth trying, but asking any proxy to hold a 22-minute request open is a poor bet, and a
success there would be luck rather than a repair.

It also sharpens the timeline: the queue worked before the 2026-08-24 Colab base image update and
has not worked since. That is the same event that produced BUG-0013, BUG-0015 and BUG-0019, and it
is exactly when `starlette` and `anyio` would have moved — the two packages nobody pins, and the
layer gradio's queue is built on.

The `anyio==3.7.1` experiment is therefore promoted from "next idea" to **the** next step: it is two
minutes on a warm runtime, and if it lands, batch 50 comes back with it.
