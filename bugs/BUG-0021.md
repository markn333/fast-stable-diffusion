# BUG-0021: generation results never reach the browser — gallery clears on completion, Save fails with `JSONDecodeError`
- Date: 2026-08-26
- Status: Workaround shipped (`--no-gradio-queue`), pending confirmation on Colab
- Severity: High

## Symptom

Image generation works — but nothing comes back to the page.

1. During generation the image is visible; **the moment it completes the gallery area goes blank.**
2. Pressing **Save** ("save the image to a dedicated directory") errors:

```
*** Error completing request
*** Arguments: ('', [], False, -1) {}
    File "modules/ui_common.py", line 76, in save_files
      data = json.loads(js_data)
    json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

The images themselves are fine: `Model loaded in 266.9s`, twenty batches of `100% 20/20`, and the
PNGs are on Drive under `outputs/txt2img-images/`. No traceback is printed when generation finishes.

## Root Cause

`*** Arguments: ('', [], False, -1)` is the whole diagnosis. Those are the inputs A1111 binds to the
Save button:

```python
save.click(
    fn=call_queue.wrap_gradio_call(save_files),
    _js="(x, y, z, w) => [x, y, false, selected_gallery_index()]",
    inputs=[generation_info, result_gallery, html_info, html_info],
    ...
)
```

- `generation_info` = `''` — should hold the generation parameters as JSON
- `result_gallery` = `[]` — **the gallery is genuinely empty**, not merely blank on screen

Both are outputs of the txt2img event. They are empty because **the result of that event never
arrived in the browser**, so the components still hold their initial values and the browser sends
those back when Save is clicked. The blank gallery follows from the same fact: A1111 draws the live
preview as a separate overlay element on top of the gallery (`progressbar.js`) and removes it when
generation ends — revealing the gallery underneath, which was never populated.

So one cause explains both symptoms, and it is a **transport** failure, not a generation failure.

gradio 3.41.2 delivers event results over a **websocket**:

```python
# gradio/routes.py
from starlette.websockets import WebSocketState
@app.websocket("/queue/join")
    await websocket.accept()
    ...
```

The stack around that websocket has drifted far from what gradio 3.41.2 was built against:

| component | what gradio 3.41.2 / A1111 expect | what the current notebook installs |
|-----------|-----------------------------------|-----------------------------------|
| starlette | 0.26.x (A1111 pins `fastapi==0.94.0`) | **0.40–0.50** (via our `fastapi==0.125.0`, BUG-0016) |
| websockets | `<12.0` (gradio's own pin) | 11.0.3 — pure-python wheel, no cp313 build |
| uvicorn | `>=0.14.0`, unpinned | 0.52.4, which **unconditionally** selects its sans-I/O websocket implementation |

A websocket that closes or drops a message produces **no traceback** — disconnects are ordinary
events — which is exactly why generation completes silently and nothing appears.

## Workaround shipped

A1111 has a first-class switch for this:

```
--no-gradio-queue   Disables gradio queue; causes the webpage to use http requests instead of
                    websockets; was the default in earlier versions
```

```python
# webui.py
if not cmd_opts.no_gradio_queue:
    shared.demo.queue(64)
```

The Start cell now exposes it as a notebook parameter, defaulting to on:

```python
Disable_Gradio_Queue = True #@param {type:"boolean"}
queue_arg = "--no-gradio-queue" if Disable_Gradio_Queue else ""
```

and passes `$queue_arg` to all three launch invocations.

This sidesteps the websocket entirely and costs very little: A1111 does not use the gradio queue for
progress — live previews and the progress bar come from its own `/internal/progress` HTTP endpoint,
so they keep working.

**It is also the experiment.** Leaving the box ticked and unticking it is a single-variable A/B:

- gallery works with the box ticked, breaks unticked → confirmed, the websocket transport is the
  fault, and the flag is a legitimate permanent answer (upstream calls it the earlier default)
- broken either way → the transport is innocent and the fault is in the event result itself; the
  next step is the browser's Network → WS tab to read the `process_completed` payload

/usr/bin/xdg-open: 882: www-browser: not found

That is the **Open folder** button asking the Colab VM to open a file manager. There is no desktop
there. Harmless, unrelated, and not worth suppressing.

## Prevention

- **A silent failure is still a lead.** No traceback at completion was the most informative signal in
  this investigation: it ruled out generation and saving, and pointed at a transport where
  disconnects are not errors.
- **Read the arguments in `*** Error completing request`.** A1111 prints the bound inputs, and
  `('', [], False, -1)` said the component state was empty before any theory was needed.
- When a version pin is chosen for one property, note what was *not* verified. BUG-0016 picked
  `fastapi==0.125.0` as "the newest release that still supports pydantic v1", and the import chain
  was checked — but the queue websocket was not, and A1111 pins `fastapi==0.94.0` precisely because
  the whole starlette layer moves with it.
