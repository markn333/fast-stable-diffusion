# BUG-0024: the ngrok tunnel dials `[::1]:7860` and is refused — `ngrok.connect(7860)` resolves through `localhost`
- Date: 2026-08-27
- Status: **Fixed — confirmed on Colab 2026-08-27.** The tunnel now reaches webui; generation through it is still untested
- Severity: Medium (ngrok path only; the default gradio.live path is unaffected)

## Symptom

The tunnel comes up and prints its URL, but nothing is reachable through it:

```
Ngrok URL: https://postcentral-cleistogamously-mariam.ngrok-free.dev
WARNING:pyngrok.process.ngrok: msg="failed to open private leg"
  privaddr=localhost:7860 err="dial tcp [::1]:7860: connect: connection refused"
```

An external `GET /config` through the tunnel returns **502 Bad Gateway**.

## Root Cause

`pyngrok` turns a bare port into a `localhost` URL:

```python
# pyngrok/ngrok.py:293
url = addr if "://" in addr else (
    f"tcp://localhost:{addr}" if proto == "tcp" else f"http://localhost:{addr}"
)
```

So `ngrok.connect(7860, ...)` asks the agent to forward to **`http://localhost:7860`**, and the
agent resolves `localhost` itself. On a host that answers with the IPv6 loopback first, it dials
`[::1]:7860`.

webui listens on IPv4 only — gradio binds `127.0.0.1` and the notebook passes no `--listen` — so
nothing is on `::1`, and the connection is refused. This is not a startup race: it does not resolve
once webui finishes booting, because there will never be anything on that address.

## Fix

Name the address explicitly instead of letting `localhost` be resolved. Since pyngrok passes any
string containing `://` through untouched, a full URL is enough:

```python
srv = ngrok.connect('http://127.0.0.1:7860', pyngrok_config=..., bind_tls=True).public_url
```

## How it was found

By testing the ngrok path **because the repository is public and has stargazers** — shipping an
unverified code path to other people was the objection, and it was the right one. The `Ngrok URL:`
line added earlier in this session had never been run even once.

Two things made the diagnosis quick rather than another multi-day hunt:

- the warning names the address it dialled, `[::1]:7860`, and the bracket notation is the whole tell
- an external probe through the tunnel returned a plain **502**, not ngrok's browser interstitial —
  which separately confirmed that non-browser User-Agents pass straight through, so the queue's own
  internal `POST /api/predict` will not be served an HTML warning page (the failure mode feared in
  BUG-0021's ngrok review)

## Prevention

- **A bare port is an invitation for someone else to resolve a hostname for you.** When handing a
  local service to a tunnel, container or proxy, name the interface: `127.0.0.1:PORT`, not `PORT`
  and not `localhost:PORT`. IPv4-only listeners plus IPv6-first resolution is a standing trap.
- **`[::1]` in an error message means the resolution went a way you did not intend.** It is worth
  reading the address in a connection-refused message rather than assuming the service is simply not
  up yet.
- Code paths that are shipped but never executed are not "probably fine". This one was added and
  documented in the same session that broke it, and it had a permanent defect.
