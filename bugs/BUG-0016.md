# BUG-0016: `ImportError: cannot import name 'IncEx' from 'pydantic.main'` — unpinned FastAPI dropped Pydantic v1 support
- Date: 2026-08-25
- Status: Resolved (fix committed, not yet verified on Colab)
- Severity: High

## Symptom

WebUI dies at the very first import, before anything else runs:

```
File "modules/initialize.py", line 23, in imports
  import gradio
File "gradio/components/base.py", line 20, in <module>
  from fastapi import UploadFile
...
File "fastapi/types.py", line 7, in <module>
  from pydantic.main import IncEx as IncEx
ImportError: cannot import name 'IncEx' from 'pydantic.main'
  (/usr/local/lib/python3.13/dist-packages/pydantic/main.cpython-313-x86_64-linux-gnu.so)
```

Surfaced immediately after the BUG-0015 fix landed. The `.so` filename in the error message is
itself the good news: `main.cpython-313-...so` is the **pydantic 1.10.22 cp313 wheel**, so the
BUG-0015 downgrade worked. The failure is now on the other side of the pair.

## Root Cause

The Requirements cell installed **fastapi unpinned**, inside the bulk line:

```python
!pip install blendmodes clean-fid einops facexlib fastapi inflection jsonmerge lark ... -qq
```

AUTOMATIC1111's `requirements_versions.txt` pins `fastapi==0.94.0`, and it does so because webui
needs Pydantic v1 (`modules/api/models.py` uses `DynamicModel.__config__`, see BUG-0015).

**FastAPI removed Pydantic v1 support in 0.126.0.** From that release on, `fastapi/types.py` does
`from pydantic.main import IncEx`, and `IncEx` exists only in Pydantic v2. Colab's unpinned install
picked up 0.141.x, so the moment pydantic went back to 1.10.22 the pair became unsatisfiable.

Verified against PyPI metadata across every release from 0.118.0 up:

| fastapi | declared pydantic constraint |
|---------|------------------------------|
| 0.94.0 – 0.125.0 | `pydantic <2.0` … `pydantic!=…,<3.0.0,>=1.7.4` → **v1 accepted** |
| 0.126.0 – 0.141.1 | `pydantic>=2.9.0` → **v2 only** |

Confirmed in the artifact, not just the metadata — `fastapi-0.125.0-py3-none-any.whl` still ships
the v1 code path (`fastapi/_compat/v1.py` with `if not PYDANTIC_V2:`, and a `types.py` that defines
`IncEx` locally instead of importing it from pydantic).

## Fix

`fast_stable_diffusion_AUTOMATIC1111.ipynb`, Requirements cell:

- removed `fastapi` from the bulk unpinned line
- added a pinned install next to the pydantic pin, where the pairing is visible:

```python
!pip install pydantic==1.10.22 --no-deps -qq
# fastapi must match pydantic. FastAPI dropped pydantic v1 in 0.126.0 ...
!pip install fastapi==0.125.0 -qq
```

- added `fastapi` to the post-install check, so a mismatch is reported by the Requirements cell
  rather than by a traceback

### Why 0.125.0 and not A1111's own `fastapi==0.94.0`

0.94.0 is what webui pins, but it drags `starlette<0.27` — a March 2023 stack that has never seen
Python 3.13. The pre-BUG-0015 Colab run is direct evidence the other way: with **fastapi 0.141 +
modern starlette** the whole import chain (`gradio` → `fastapi` → `starlette`) completed fine on
Python 3.13, and `modules/api/api.py` imported too. The only thing that had to change was Pydantic
v1 support, so the newest release that still has it is the smallest step away from a
known-working import chain.

## Audit: is anything else going to fail on import?

Every package the notebook installs, plus the ones webui reaches indirectly, was checked against
its PyPI `requires_dist` for a Pydantic constraint:

| package | pydantic constraint | status |
|---------|---------------------|--------|
| `fastapi` (latest) | `pydantic>=2.9.0` | **was the bug** — now pinned to 0.125.0 |
| `gradio` (latest 6.x) | `pydantic<=3.0,>=2.0` | safe — pinned to `3.41.2`, which wants `>=1.7.4,<3.0.0` |
| `wandb` (latest 0.28) | `pydantic<3,>=2.6` | safe — pinned to `0.15.12` **and** `--no-deps` |
| `transformers` | `pydantic>=2` only under the `serving` / `dev` / `testing` extras | safe — extras not installed |
| gradio-client 0.5.0, altair, huggingface-hub, spandrel, uvicorn, starlette, diffusers, accelerate, open-clip-torch, pytorch-lightning, controlnet-aux, invisible-watermark, fire, fairscale | none | safe |

**No other package in the stack requires Pydantic v2.** fastapi was the only remaining one.

Separately, every pinned version in the notebook was re-checked for Python 3.13 installability
(the BUG-0015 failure mode): `gradio==3.41.2`, `protobuf==3.20.0`, `wandb==0.15.12` resolve to
pure-python wheels; `pydantic==1.10.22` and `scipy==1.15.3` have cp313 wheels; `fastapi==0.125.0`
is pure-python. No pin in the notebook now requires a source build.

Known remaining drift, none of it import-breaking today (webui reached model loading with these
versions installed, so they import): the notebook installs `einops`, `kornia`, `open_clip_torch`,
`pytorch_lightning`, `safetensors`, `scikit-image`, `psutil`, `GitPython`, `accelerate` unpinned
while A1111 pins them. Most of A1111's pins cannot be honoured on Python 3.13 anyway
(`Pillow==9.5.0`, `numpy==1.26.2`, `psutil==5.9.5`, `scikit-image==0.21.0`, `pillow-avif-plugin==1.4.3`
are all sdist-only there). These are the next candidates if a future Colab image breaks something.

## Prevention

- **Pin both halves of a version-coupled pair, next to each other.** pydantic and fastapi are one
  decision, not two; pinning only pydantic moved the break rather than fixing it.
- When a package is in webui's `requirements_versions.txt`, either pin it or record why not. `fastapi`
  was pinned upstream for exactly this reason and the notebook silently overrode that with "latest".
- Check the artifact, not only the metadata, when a compatibility boundary matters: PyPI metadata
  said 0.125.0 allows v1; unpacking the wheel and finding `_compat/v1.py` is what makes that a fact.
