# BUG-0023: gradio's queue calls its own `/api/predict` with httpx's default 5-second timeout, so every generation is reported to the browser as failed
- Date: 2026-08-27
- Status: **Resolved — verified on Colab 2026-08-27.** With the patch applied and the queue enabled, the image appears in the gallery
- Severity: High
- Root cause of: BUG-0021

## Symptom

See BUG-0021: generation completes, the PNG is written to Drive, no traceback appears anywhere, and
the page shows nothing — blank gallery, dead PNG Info, `Save` receiving `('', [], False, -1)`.

## Root Cause

**gradio's queue does not run the prediction in-process. It POSTs to its own HTTP API and waits.**

```python
# gradio/queueing.py
self.queue_client = httpx.AsyncClient(verify=ssl_verify)      # line 80
...
response = await AsyncRequest(
    method=AsyncRequest.Method.POST,
    url=f"{self.server_path}api/predict",                     # line 376
    json=dict(data),
    client=self.queue_client,
)
```

`httpx.AsyncClient()` built with no `timeout` argument uses **`Timeout(timeout=5.0)`** — verified by
installing httpx 0.24.1 and asking it. `AsyncRequest` passes no timeout of its own
(`await self.client_.send(self._request)`).

**So any prediction taking more than five seconds times out.** Every image generation does; this one
took 48 seconds.

What happens next is why nothing was ever visible:

```python
except Exception as exception:
    # If there is an exception, store it to do further inspections.
    self._exception = self._exception_type(exception)
```

`AsyncRequest`'s own docstring says it plainly: *"Exceptions are handled silently during the request
call."* The `ReadTimeout` is captured, never printed, never raised. Then:

```python
if response.has_exception:
    for event in awake_events:
        await self.send_message(event, {
            "msg": "process_completed",
            "output": {"error": str(response.exception)},
            "success": False,
        })
```

The queue tells the browser the job **failed**. The browser is behaving correctly: it does not apply
the outputs of a failed job, so the gallery stays empty and every component keeps its initial value —
which is exactly what `Save` sent back as `('', [], False, -1)`.

Meanwhile the actual prediction is still running server-side, finishes normally, writes the PNG and
logs nothing unusual. Server and browser are each behaving correctly and neither has anything to
report. That is the whole of BUG-0021.

### How it was cornered

Two instruments, after every version hypothesis had failed:

1. **An external websocket client** driving `/queue/join` in the browser's place. It reached
   `process_completed` with real data in **2.07 s** — proving the queue, the tunnel and the websocket
   were all healthy. Crucially it used a zero-input dependency that returns in ~0.6 s, **inside the
   five-second window**, which is why it succeeded where the browser failed.
2. **Patching `send_message` to print its swallowed exception.** A browser generation then produced
   *no* output from it — so the send had succeeded. That eliminated the send path and left only the
   payload: a `process_completed` carrying `success: False`.

The gap between "the queue delivers in 2 seconds" and "the browser gets nothing from a 48-second
job" is the five-second timeout, and nothing else.

## Fix

The Start cell patches `gradio/queueing.py` before launch:

```python
self.queue_client = httpx.AsyncClient(verify=ssl_verify)
# ->
self.queue_client = httpx.AsyncClient(verify=ssl_verify, timeout=None)
```

Two diagnostics are applied alongside it, so this class of failure can never be silent again:

- `call_prediction` failures print the exception type and message
- `send_message` failures print the exception type and message

All three were verified against the real `gradio/queueing.py` from the 3.41.2 wheel: each pattern
matches, and the patched file compiles.

## Prevention

- **A library's default timeout is a decision it made for you.** `httpx.AsyncClient()` looks
  timeout-free and is not; five seconds is fine for an API call and absurd for an inference job.
  When a client is constructed without an explicit timeout, that is a bug waiting for a slow
  operation.
- **Two silent handlers stacked on top of each other cost days here.** `AsyncRequest` swallows the
  exception by design, and `send_message` swallows its own. Neither printed. When a subsystem
  "does nothing quietly", instrument the swallowing code rather than reasoning about the versions
  around it — the patch that found this was four lines.
- **An external client is a cheap oracle.** Speaking the protocol directly separated server from
  browser in two seconds, after days of inferring transport behaviour from a page's symptoms. Reach
  for it early.
- The version hunt was not wasted, but it was the wrong instrument: pins were tested for
  `fastapi`, `starlette`, `anyio`, `uvicorn`, `websockets`, `transformers` and `open_clip` before a
  single line of gradio's own delivery path was read.

## Why it used to work: this was most likely self-inflicted

The obvious objection to the diagnosis above is that a five-second timeout would have broken **every**
generation ever, yet batch 50 ran fine days ago. The answer appears to be that **gradio was not
3.41.2 back then**.

The notebook has always done `rm -r .../gradio*` in the Requirements cell and then let whatever came
out of TheLastBen's `gcolabdeps.tar.zst` (or Colab's image) provide gradio. It only began *pinning*
`gradio==3.41.2` with the BUG-0014 fix on 2026-08-25 — a change made in this same investigation.

And the internal HTTP call is specific to 3.41.x. Checked across the wheels:

| gradio | `IOComponent` (webui needs it) | `pil_to_temp_file` (webui needs it) | queue POSTs to its own `api/predict` |
|--------|-------------------------------|-------------------------------------|--------------------------------------|
| **3.41.2** | yes | yes | **yes** |
| 3.44.4 | yes | yes | **no** |
| 3.50.2 | yes | yes | **no** |

gradio removed the self-call in 3.44 and runs the prediction in-process instead — its own source
notes it now decodes the result *"emulating the HTTP client behavior"*. So upstream treated this
design as a problem and replaced it.

If the pre-08-24 environment carried any 3.44–3.50 build, the queue had no HTTP call, no httpx
client and no five-second ceiling, and long generations worked exactly as the user remembers.
Pinning to 3.41.2 to fix BUG-0014 would then have introduced this one.

That is a hypothesis, not a proven fact — the gradio version present before 2026-08-24 was never
recorded. But it is consistent with every observation, and it identifies a second, cleaner fix.

### Two ways to fix this

| | approach | trade-off |
|---|----------|-----------|
| **A** (shipped) | keep `gradio==3.41.2`, patch its queue client to `timeout=None` | matches A1111's own pin; relies on a monkey-patch of a third-party file |
| **B** | pin `gradio==3.50.2` instead | uses upstream's own fix, no patching; but deviates from the version webui pins, so other differences are untested |

A is shipped because it is the smaller change and matches what webui expects. B is the fallback if A
does not hold up, and is the tidier long-term answer — both `IOComponent` and `pil_to_temp_file`,
the two gradio internals webui reaches into, still exist in 3.50.2.

## Verified 2026-08-27

Run with all three switches off — queue enabled, extensions on, TheLastBen's blocks.py — and the
patch reported applied at launch:

```
  gradio patch: queue client timeout removed (BUG-0023)
  gradio patch: call_prediction failures now logged
  gradio patch: send_message failures now logged
```

**The image appears in the gallery.** The queue delivers again.

Cleanup applied with the fix:

- `Disable_Gradio_Queue` back to **False**. It is now only an escape hatch — turning it on makes each
  generation a single synchronous POST, which the tunnel 504s after a few minutes.
- The launch warning was saying the opposite of the truth (*"gradio queue is ENABLED - results will
  not reach the page"*). It now fires on the **disabled** case and explains the 504 trade-off.
- The two diagnostics stay in permanently. They cost nothing when nothing is wrong, and they are the
  reason this was found at all.

Still to confirm: **batch 50**, which is what started this. With the queue restored a generation is
no longer one long HTTP request, so the 504 ceiling should be gone.
