# BUG-0022: `<Queue ...> is bound to a different event loop` — uvicorn's sans-I/O websocket implementation breaks gradio's queue, so no result ever reaches the browser
- Date: 2026-08-26
- Status: Resolved (fix committed, not yet verified on Colab)
- Severity: High
- Root cause of: BUG-0021

## Symptom

```
<Queue at 0x7aca9b4c6fd0 maxsize=0 tasks=2> is bound to a different event loop
<Queue at 0x7aca9b3b4770 maxsize=0 tasks=2> is bound to a different event loop
... (one per connection)
```

One line per websocket connection, no traceback. Downstream of it: the gallery blanks the moment
generation completes, **PNG Info stops working**, and Save fails with `('', [], False, -1)` —
i.e. every gradio event result fails to arrive, while clicks travelling the other way work fine.

The lines only became visible after launching with `--disable-extra-extensions`. With ADetailer,
ControlNet and the rest loaded, they were buried in extension chatter.

## Root Cause

Two facts, both confirmed by running the code rather than reading it:

**1. uvicorn ≥ 0.50 always selects its sans-I/O websocket implementation.** Its `auto.py` is not a
version check — if `websockets` imports at all, sansio wins:

```python
try:
    import websockets  # noqa
except ImportError:
    ...wsproto...
else:
    from uvicorn.protocols.websockets.websockets_sansio_impl import WebSocketsSansIOProtocol
    AutoWebSocketsProtocol = WebSocketsSansIOProtocol
```

and that implementation creates a **per-connection `asyncio.Queue` on uvicorn's own event loop**:

```python
# uvicorn/protocols/websockets/websockets_sansio_impl.py
self.queue: asyncio.Queue[ASGIReceiveEvent] = asyncio.Queue()
```

**2. gradio 3.41.2 runs its queue coroutine on a different loop.** `blocks.py` starts the server in
a thread (`networking.start_server`, which gives uvicorn its own loop) and separately does:

```python
utils.run_coro_in_background(self._queue.start, self.ssl_verify)
```

When gradio's queue then touches uvicorn's per-connection Queue, `asyncio.mixins._LoopBoundMixin`
raises `RuntimeError: <Queue ...> is bound to a different event loop`.

**And gradio swallows it.** `gradio/queueing.py:464` is a bare:

```python
print(e)
```

No traceback, no error to the client, no failed request — just one line of console output and a
result that is never delivered. That single `print(e)` is why this bug looked, for days, like a
silent transport failure with healthy servers on both sides.

### Verified locally, not inferred

Both combinations were installed in a throwaway venv and asked what they select:

| installed | selected implementation | per-connection `asyncio.Queue` |
|-----------|------------------------|--------------------------------|
| uvicorn **0.52.4** + websockets 11.0.3 | `websockets_sansio_impl` | **yes** |
| uvicorn **0.49.0** + websockets 11.0.3 | `websockets_impl` (legacy) | no |

Reading the wheels had suggested the legacy implementation could not even import against
websockets 11 (`from websockets.server import WebSocketServerProtocol`, which the wheel's
`server.py` appears not to export). Installing it proved otherwise. The archaeology was wrong; the
experiment was cheap.

## Fix

`fast_stable_diffusion_AUTOMATIC1111.ipynb`, Requirements cell, next to the gradio pin the stack
belongs to:

```python
!pip install gradio==3.41.2 -qq
!pip install uvicorn==0.49.0 -qq
```

0.49.0 is the **last** release defaulting to the legacy implementation — 0.50.0 is the first to
switch, located by bisecting every release between 0.36.0 and 0.52.4. It ships a pure-python wheel
with `requires_python >=3.10`, so Python 3.13 is fine.

`uvicorn` and `websockets` are now both in the Requirements cell's post-install check. websockets
itself needs no pin: gradio 3.41.2 already constrains it to `<12.0`, and the legacy implementation
needs `websockets.legacy`, which exists there.

## Expected effect

Everything in BUG-0021 should resolve at once, since all of it was one undelivered result:

- the gallery keeps the image after generation
- PNG Info works again
- Save receives real values instead of `('', [], False, -1)`

`--no-gradio-queue` should no longer be needed, and it should stay off: it swaps the websocket for
one long synchronous POST that the gradio.live tunnel kills with a 504 on any real generation.

## Prevention

- **`print(e)` in a library is an invisibility cloak.** The whole of BUG-0021 — days of it — was one
  swallowed `RuntimeError`. When a subsystem "silently does nothing", grep the library for bare
  prints of exceptions before theorising about transports.
- **Turning off the noise is a diagnostic step, not just tidiness.** These lines were always being
  printed; `--disable-extra-extensions` is what made them readable.
- **Install it and ask, don't read the wheel and guess.** The wheel inspection here reached the
  wrong conclusion about whether the legacy implementation could import. A venv and two commands
  settled it in seconds.
- Add `uvicorn` to the list of things A1111's stack is sensitive to. Neither A1111 nor gradio pins
  it (gradio only asks for `>=0.14.0`), yet the choice of websocket implementation decides whether
  gradio's queue works at all.
